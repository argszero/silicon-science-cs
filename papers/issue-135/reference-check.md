# Reference check -- issue #135

**What this file is.** The verification report for the reference layer of issue #135 (*The Load
Factor Is Not the Tail: Exact Probe-Count Operating Characteristics and the Budget Boundary of
Bounded Open-Addressing Hash Tables*). Every entry in the pool was discovered by `refscan135.py` --
nothing is typed from memory -- and each was checked against a **live external record** by
comparing the returned **title** with the stored title.

**Result: 556 / 556 VERIFIED, 0 title mismatch, 0 transport-unknown.** The pool holds **556**
entries (543 arXiv, 13 Crossref), well above the journal's 100-reference floor. The full per-entry
table is `reference-pool.md`; the machine-readable pool is `refs/pool.json`; the verbatim output of
the verification run is the committed receipt `refs/verify-run.txt`. The **cited subset** is pinned
when the manuscript is composed, from this same pool and this same check.

## Method

| Source | Use | Endpoint |
|---|---|---|
| arXiv API | discovery | `search_query=<topic>` -- 40 queries derived from this paper's own subject (open addressing, linear probing, Robin Hood hashing, cuckoo hashing/filters, probe counts, load factor, balls-into-bins, universal/tabulation hashing, succinct and perfect hashing, cache-conscious tables, tail bounds) |
| arXiv API | verification | `id_list=<ids>` in batches of 20, `max_results` set to the batch size |
| Crossref | canonical works, found **BY TITLE** | `query.bibliographic=<title>` |
| Crossref | verification | `works/<doi>` |

**Why a title match and not the HTTP status.** A DOI or an arXiv id written from memory *resolves*:
the endpoint returns 200 with a **real** record -- of a **different** paper. So the check is the
returned title against the stored title, scored as the **smaller** of the two coverage fractions
(a one-sided score lets a short generic title reach 1.00 against a long specific one, i.e. a metric
that can never fail on the object it is built to catch). Threshold **0.80**. Every canonical work is
found **by title**, never by a remembered identifier.

**Transport failures are not findings.** An API outage yields `TRANSPORT-UNKNOWN`, never "these
records do not exist", and fails the run. The final pass is `0`.

## Defects found and repaired while building this layer

1. **A canonical record the bare title does not reach.** `Fast Hash Table Lookup Using Extended
   Bloom Filter` came back `WEAK 0.78` against a *different* real paper. Crossref stores this
   record's two parts joined (`title` = `Fast hash table lookup using extended bloom filter`,
   `subtitle` = `an aid to network processing`), and the bibliographic search ranks the bare main
   title's other candidates first, so the record itself never entered the candidate set. Fixed by
   naming the **subtitle** in the query: the exact record then ranks first and the two-sided match
   is **1.00**. (The reader already joins `title` + `subtitle`; the fix is to the *query*.)
2. **A work neither registry indexes.** `Why Simple Hash Functions Work: Exploiting the Entropy in a
   Data Stream` (2008) was verified **absent** from both Crossref (by title, by author, and by exact
   `query.title`) and arXiv (by `ti:` and by `all:`, and by author) -- a SODA/SICOMP-era paper
   neither registry carries under that title. An unverifiable citation cannot be cited, so the
   entry was **dropped**, never admitted on a weak match against a different real paper (the exact
   defect `title_matches` exists to catch: a remembered title resolving to someone else's work).
3. **One paper, two records.** The pool carried three duplicate titles: two works that arrive both
   as an arXiv preprint **and** as a published DOI, and one paper posted to arXiv under two ids.
   A duplicate title lets the manuscript cite one paper as two references, so the collision is
   resolved deterministically and the policy is stated -- a Crossref (published) record wins over an
   arXiv preprint of the same title, and between two records of the same source the **earlier**
   publication date wins. Repaired by `curate()`; the offline gate asserts the pool has no duplicate
   title.
4. **A receipt that outlives its pool.** The verification receipt is the only evidence the network
   pass ran, so it is made offline-checkable: its first line is `POOL sha256 <hex>`, and the offline
   gate fails when that digest no longer matches the shipped `refs/pool.json`. This fired during the
   build (after the dedup changed the pool) and demanded the re-run -- a quoted receipt is a claim
   about a program until it names its own input (Class 192 / Class 230).

## What this check does **not** establish

- It is a **harvest regression check on identity**, not independent identity evidence: the stored
  title and the live title are read from the same backend field, so a perfect score is expected
  when the harvest is intact. It rules out a *wrong* record, not a systematically mislabelled one.
- It says nothing about **relevance** (the curation filter does that). An entry in the pool is not
  yet a reference: which entries the manuscript cites, and whether **every** entry it prints is
  cited in the body, is the journal reference gate's reading -- quoted verbatim in its own section
  above, not established here.
- The 13 Crossref entries are canonical works found by title; the 543 arXiv entries are discovered
  by topic query and curated by the CORE/SUPPORT term filter. The pool is broader than the final
  bibliography on purpose -- the manuscript cites the subset it argues with, and pins that subset
  here when it is composed.
